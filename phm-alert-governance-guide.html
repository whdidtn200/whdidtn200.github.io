PHM Alert Governance Guide

모델 점수를 정비 행동으로 바꾸려면 임계치보다 먼저 상태, 책임자, 증거, 작업 지시와 종결 기준이 필요합니다. 이 가이드는 경보 한 건이 생성돼 닫힐 때까지의 운영 구조를 정리합니다.

Updated 2026-07-17PHM OperationsAlert Lifecycle90-day rollout

핵심: 모델 점수는 계산 결과이고 경보는 운영 객체입니다. 누가 언제 어떤 근거로 무엇을 확인해야 하는지, 어떤 결과로 닫혔는지까지 남지 않으면 경보가 많아도 예지보전 체계가 아닙니다.

여섯 단계 상태 모델

1. Observe점수와 속도·하중·환경 조건을 함께 저장
2. Qualify지속성, 중복, 센서 건강도, 정비 mode 확인
3. Triage위험과 운행 영향으로 우선순위·owner 지정
4. Inspect파형·추세·정비 이력·현장 증거 결합
5. Act작업 지시, 제한, 추가 계측, 관찰 유지 결정
6. Close결과 label과 근거를 baseline에 반환

경보 레코드의 최소 필드

  • alert_id, 자산·부품·센서, 발생·확인·종결 시각
  • 모델·feature·threshold 버전과 입력 데이터 품질 상태
  • 속도, 하중, 노선, 계절, 운전 mode 같은 context
  • baseline 대비 변화량, persistence 결과, confidence
  • severity, owner, due time, escalation rule
  • inspection, work order, 교체 부품, 실제 발견 결함
  • true positive, false positive, inconclusive, sensor issue 종결 label

Severity와 Confidence를 분리하라

Severity는 틀렸을 때의 영향이고 confidence는 현재 증거의 강도입니다. 안전 영향이 큰 저신뢰 경보는 무시할 대상이 아니라 추가 센서 확인이나 짧은 재측정으로 보내야 합니다.

Severity의미기본 행동
S1추세 관찰다음 주기까지 watch
S2성능 저하 가능원격 검토와 추가 데이터
S3정비 필요 가능성inspection ticket
S4안전·운행 영향 가능즉시 escalation

Persistence와 억제 규칙

단일 초과 경보는 이벤트 단위 오경보를 키울 수 있습니다. `2-of-3`, `3-of-5`, hysteresis, cooldown을 자산별로 조합하되 탐지 지연을 함께 측정해야 합니다. 계획 정비, 시운전, 센서 장애, 동일 root cause의 중복 경보는 삭제하지 말고 `suppressed` 상태와 이유를 기록합니다.

실험 연결: MALT의 10,000개 이벤트 실험에서 복합 조건 정상 이벤트 오경보는 `1-of-1` 96.8%에서 `3-of-5` 32.7%로 줄었지만 중앙값 1 window의 탐지 지연이 생겼습니다. 규칙은 숫자만 복사하지 말고 window 길이와 고장 진행 시간을 함께 정해야 합니다.

역할과 승인 경계

  • Data/PHM engineer: threshold, 모델·feature 버전, drift 관리
  • Maintenance planner: inspection 우선순위와 일정 결정
  • Field maintainer: 실제 상태, 조치, 부품 기록
  • Operations controller: 운행 영향과 즉시 대응 결정
  • Asset owner: 위험 수용, 정책 변경, KPI 승인

AI는 후보 묶기, 관련 이력 찾기, 설명 초안, 반복 경보 요약을 보조할 수 있습니다. 안전 영향이 있는 작업 지시와 운행 제한은 책임자의 승인 경계를 유지합니다.

경보 품질 KPI

  • Alert-to-inspection conversion과 confirmed finding rate
  • Detection lead time과 time to acknowledge/triage/close
  • 자산·노선·근무조별 nuisance burden
  • 종결 후 repeat alert rate
  • label 없이 닫힌 unknown outcome rate

정확도와 F1만으로는 정비 부담, 지연, 미종결 사건을 설명할 수 없습니다.

주간 경보 리뷰 회의 양식

주간 리뷰는 모델 성능 발표가 아니라 경보 정책을 조정하는 운영 회의여야 합니다. 지난 7일의 신규 경보, 미종결 경보, 반복 경보, false positive 상위 자산을 먼저 보고 각 경보에 owner, 다음 행동, 기한을 붙입니다. 회의에서 threshold를 즉시 바꾸기보다 변경 후보와 근거를 별도 queue에 남깁니다.

  • 바로 점검할 경보와 관찰을 유지할 경보를 분리합니다.
  • 센서 문제, 운전 조건 변화, 모델 drift 중 원인 가설을 기록합니다.
  • threshold 또는 persistence 변경의 예상 효과와 rollback 기준을 정합니다.
  • 종결 label이 없는 과거 경보의 보완 담당자와 기한을 지정합니다.

경보 payload에는 model_version, threshold_version, context, persistence, severity, owner, linked_work_order, closure_label을 포함합니다. 이 구조가 있어야 정책 변경 전후를 비교하고 문제가 생겼을 때 어느 버전으로 되돌아갈지 판단할 수 있습니다.

30·60·90일 도입 순서

30일: 자산 한 종류, severity 두 단계, record schema, owner, 종결 label을 만듭니다. 60일: persistence와 suppression reason을 적용하고 주간 false alarm review를 시작합니다. 90일: CMMS 작업 지시와 연결하고 threshold 변경 전후의 workload와 lead time을 비교합니다.

모델 재학습은 마지막입니다. 점검 결과가 안정적으로 돌아오지 않는 상태에서 재학습부터 자동화하면 잘못된 label을 더 빠르게 증폭할 수 있습니다.

한계와 적용 범위

이 가이드는 특정 철도 운영사의 안전 규정이나 승인 절차를 대체하지 않습니다. 자산 위험 등급, 법규, 운행 규칙에 맞춰 severity와 승인 경계를 다시 정의해야 합니다.
