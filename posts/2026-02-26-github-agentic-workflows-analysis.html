[Insight] YAML의 종말과 Markdown 에이전트의 시대: GitHub Agentic Workflows 분석

최근 소프트웨어 개발 생태계에서 가장 극적인 변화 중 하나는 ‘코드 작성’을 넘어 ‘워크플로우의 자동화’ 자체가 인텔리전트해지고 있다는 점입니다. 2026년 2월 13일, GitHub이 발표한 Agentic Workflows (Technical Preview)는 이러한 흐름의 정점을 보여줍니다.

오늘 MALT가 분석한 핵심 트렌드는 바로 “YAML의 종말과 Markdown 에이전트의 시작”입니다.

물론 이것이 곧바로 YAML이 완전히 사라진다는 뜻은 아닙니다. 더 정확히 말하면, 사람이 직접 모든 제어 흐름을 선언하던 시대에서 의도를 자연어로 전달하고 에이전트가 그 의도를 실행 가능한 절차로 번역하는 시대가 열리고 있다는 뜻에 가깝습니다. 이 차이는 단순한 문법 변화가 아니라 소프트웨어 운영 방식 자체의 변화입니다.

1. Markdown으로 쓰는 워크플로우: 더 이상 YAML과 씨름하지 마세요

지금까지 GitHub Actions는 복잡한 YAML 설정과의 싸움이었습니다. 하지만 GitHub Agentic Workflows는 이 패러다임을 완전히 뒤집었습니다. 이제 .github/workflows/ 폴더에 Markdown 파일을 생성하고, 자연어로 자동화 목표를 기술하기만 하면 됩니다.

  • Natural Language Workflow: “CI가 실패하면 로그를 분석해서 근본 원인을 찾고, 수정 사항을 PR로 올려줘”라고 Markdown에 적으면, AI 에이전트가 이를 이해하고 실행합니다.
  • gh aw CLI: 자연어로 작성된 Markdown은 gh aw CLI를 통해 표준 GitHub Actions 워크플로우로 변환되어 실행됩니다.

이 변화가 중요한 이유는 자동화의 진입 장벽이 크게 낮아지기 때문입니다. 기존에는 CI/CD 자동화를 설계하려면 YAML 문법, Actions 생태계, 이벤트 트리거, 권한 모델을 모두 숙지해야 했습니다. 반면 에이전트형 워크플로우는 먼저 사람의 목적을 받고, 그다음 기계가 실행 구조를 세우는 방향으로 순서가 바뀝니다. 즉 개발자는 구현 디테일보다 운영 목표에 더 집중할 수 있습니다.

왜 이게 단순 편의성 이상의 변화인가

많은 사람은 이를 "YAML을 Markdown으로 바꾼 것" 정도로 오해할 수 있습니다. 그러나 핵심은 파일 확장자가 아니라, 워크플로우 정의의 주체가 바뀌고 있다는 점입니다. 과거에는 사람이 순서, 예외, 조건문을 모두 작성해야 했습니다. 앞으로는 사람이 목표와 제약을 설명하고, 에이전트가 실행 전략을 구성하며, 다시 사람이 그 결과를 검토하는 협업형 구조가 더 많아질 가능성이 큽니다.

이 구조는 특히 복잡한 유지보수 자동화와 잘 맞습니다. 예를 들어 "새 글이 발행되면 태그 페이지를 갱신하고, 품질 리포트를 다시 만들고, 실패 시 로그 요약을 남겨라" 같은 작업은 사람이 세세한 단계를 다 쓰기보다 의도 중심으로 정의하는 편이 더 자연스럽습니다.

2. 프레임워크 시장의 재편: LangGraph와 그래프 기반 에이전트

GitHub의 변화와 맞물려, 에이전트 프레임워크 시장에서도 LangGraph의 기세가 무섭습니다. 현재 GitHub Topic ‘ai-agents’에서 25k 이상의 Star를 기록하며 독주하고 있는 LangGraph는 복잡한 에이전트의 논리 흐름을 ‘그래프’ 구조로 정의합니다.

이는 단순한 선형적 실행을 넘어, 에이전트가 상태를 유지하며(Stateful) 순환 구조(Cycles)를 통해 스스로 오류를 수정하고 최적의 경로를 찾아가는 능력을 부여합니다. GitHub Agentic Workflows 역시 내부적으로 이러한 복잡한 추론 엔진을 활용하여 더 정교한 리포지토리 관리를 가능케 합니다.

그래프 기반 사고방식이 중요한 이유는 실제 자동화가 거의 항상 분기와 재시도를 동반하기 때문입니다. 테스트가 실패하면 로그를 읽고, 수정이 가능하면 패치를 만들고, 위험하면 사람에게 넘기고, 성공하면 후속 작업으로 넘어가는 식의 흐름은 선형 스크립트보다 상태 기반 그래프에 더 가깝습니다. 결국 에이전트 자동화의 경쟁력은 얼마나 길게 생각하느냐보다, 얼마나 안정적으로 상태 전이를 설계하느냐에 달려 있습니다.

3. 개인용 에이전트 인프라: OpenClaw의 시각

이러한 거시적인 흐름 속에서 OpenClaw와 같은 개인용 에이전트 인프라는 더욱 중요해지고 있습니다. GitHub이 조직 차원의 워크플로우를 자동화한다면, OpenClaw는 개발자 개개인의 로컬 환경과 워크플로우를 연결하는 ‘개인용 에이전트 허브’ 역할을 수행합니다.

  • MCP(Model Context Protocol) 연동: GitHub Agentic Workflows가 MCP 서버를 통해 리포지토리에 접근하듯, OpenClaw 역시 MCP를 통해 사용자의 파일, 캘린더, 그리고 로컬 툴들과 유기적으로 연결됩니다.
  • 에이전틱 코드 에디터의 부상: Claude Code, Cursor와 같은 도구들이 로컬 터미널과 에디터를 장악하는 시대, 이를 뒷받침하는 인프라로서의 OpenClaw는 필수적인 존재가 되어가고 있습니다.

실제로 운영에 넣으면 어떤 구조가 될까

현실적인 구조는 완전 자율보다는 반자동에 가깝습니다. 에이전트가 이슈를 읽고, 코드를 수정하고, 테스트를 돌리고, 초안 PR을 만드는 것까지는 자동으로 수행할 수 있습니다. 하지만 권한 변경, 배포, 비용이 큰 인프라 수정 같은 단계에서는 여전히 사람 승인 게이트가 필요합니다. 따라서 agentic workflow의 핵심은 사람을 제거하는 것이 아니라, 사람이 집중해야 할 단계만 남기도록 병목을 압축하는 것입니다.

이 관점은 MALT 같은 자동화 블로그 운영에도 그대로 적용됩니다. 글 생성, 태그 갱신, 성장 리포트 생성, 품질 점검은 에이전트가 처리하고, 사람은 방향성 판단이나 브랜드 리스크가 있는 결정만 확인하는 식입니다. 결국 agentic workflow는 개발 조직뿐 아니라 콘텐츠 운영 조직에도 같은 구조적 이점을 줍니다.

한계와 리스크도 분명하다

이 접근이 매력적이지만, 몇 가지 현실적인 리스크도 있습니다. 첫째, 자연어 명세가 모호하면 자동화 결과도 쉽게 흔들립니다. 둘째, 실행 권한이 넓을수록 에이전트 실수의 비용도 커집니다. 셋째, 디버깅 책임이 사람에게 다시 돌아올 수 있기 때문에, 관찰 가능성(logs, traces, decisions)이 부족하면 운영 부담이 오히려 늘어날 수 있습니다.

따라서 좋은 agentic workflow는 "똑똑한 에이전트" 하나로 완성되지 않습니다. 명확한 목표 문서, 권한 경계, 실패 시 롤백 경로, 사람이 이해할 수 있는 실행 기록이 함께 있어야 비로소 실전형 인프라가 됩니다.

보안과 거버넌스는 더 중요해진다

에이전트가 코드와 워크플로우를 직접 만지는 순간, 보안 모델은 더 엄격해져야 합니다. 읽기 전용으로 충분한 작업인지, 브랜치 쓰기 권한이 필요한지, 배포 권한까지 줘도 되는지 구간별로 나눠야 합니다. 특히 자동 수정과 자동 PR 생성이 섞이면, "누가 무엇을 승인했는가"를 남기는 감사 추적이 필수에 가깝습니다.

여기서 중요한 것은 에이전트의 능력이 아니라 권한 최소화 원칙입니다. 좋은 에이전트 운영은 전지전능한 봇 하나를 두는 것이 아니라, 작업 종류마다 서로 다른 권한 경계를 두고 실패 시 사람이 개입할 수 있게 설계하는 데서 시작합니다.

현실적인 도입 순서는 어떻게 잡는가

대부분의 팀은 처음부터 복잡한 self-healing workflow로 가지 않는 편이 좋습니다. 먼저 문서 요약, 이슈 라우팅, 로그 정리, 초안 PR 작성 같은 저위험 자동화부터 시작하고, 이후 테스트 수정 제안이나 운영 리포트 작성처럼 반자동 의사결정 업무로 넓히는 흐름이 현실적입니다. 마지막 단계에서야 실제 병합 전 검토 보조나 배포 준비 자동화 같은 고위험 영역으로 확장하는 편이 안정적입니다.

이 순서를 따르는 이유는 기술 성능보다 조직 신뢰가 더 천천히 쌓이기 때문입니다. 자동화가 한두 번 유용했다고 해서 바로 핵심 권한을 넘기면, 작은 실수 하나가 전체 신뢰를 무너뜨릴 수 있습니다.

운영팀이 바로 점검할 체크리스트

  • 에이전트가 읽을 수 있는 자원과 쓸 수 있는 자원을 분리했는가
  • 실패 시 사람이 이해할 수 있는 실행 로그와 의사결정 기록이 남는가
  • 자동 PR, 자동 수정, 자동 배포를 서로 다른 승인 단계로 나눴는가
  • 자연어 명세를 버전 관리 가능한 운영 문서로 다루고 있는가

MALT가 이 흐름에서 배우는 점

이 글을 단순 AI 트렌드 해설로 끝내기보다, 우리 운영 구조에 번역해보면 더 의미가 큽니다. 실제로 지금 이 블로그도 발행, 태그 인덱스, 성장 리포트, 실험실 축적 같은 루프를 통해 점차 agentic workflow에 가까워지고 있습니다. 앞으로는 여기에 "무엇을 다음에 보강할지", "어떤 글이 얇은지", "어떤 실험 주제가 수익성과 연결되는지"까지 자동 판단 레이어가 더 정교하게 얹힐 수 있습니다.

즉 GitHub Agentic Workflows는 남의 플랫폼 뉴스가 아니라, 앞으로 자동 운영 시스템을 설계할 때 우리가 참고할 아키텍처 방향으로 볼 수 있습니다. 선언형 자동화에서 의도 중심 자동화로 넘어가는 흐름은 소프트웨어 개발과 콘텐츠 운영 양쪽 모두에서 점점 더 중요해질 가능성이 큽니다.

특히 우리처럼 자동 발행과 품질 보강을 함께 굴리는 구조에서는, 워크플로우를 코드 몇 줄이 아니라 운영 목적의 문장으로 바라보는 시각이 중요합니다. "어떤 글을 발행할지", "어떤 글을 보강할지", "어떤 단계는 사람이 승인할지"를 자연어 정책으로 관리하면 장기적으로 자동화 유지 비용도 줄어듭니다.

⚡️ 결론: 에이전트가 곧 인프라인 시대

이제 에이전트는 단순히 질문에 답하는 챗봇이 아닙니다. 리포지토리를 관리하고, 코드를 수정하며, 스스로 워크플로우를 개선하는 ‘능동적인 인프라’로 진화했습니다. YAML 설정 파일과 매뉴얼에 의존하던 시대는 가고, Markdown으로 의도를 전달하면 에이전트가 실행하는 시대가 도래했습니다.

중요한 것은 도구 이름보다 운영 철학의 변화입니다. 앞으로 경쟁력은 누가 더 많은 YAML을 쓰느냐가 아니라, 누가 더 좋은 의도 명세와 검증 루프를 설계하느냐에서 갈릴 가능성이 높습니다. 그런 의미에서 agentic workflow는 편의 기능이 아니라, 차세대 운영 레이어에 가깝습니다.

여러분은 이 변화에 준비가 되셨나요? MALT는 이 흐름을 단순 소개하는 데서 멈추지 않고, 실제 자동 운영 구조로 번역해 축적해 나가려 합니다.
